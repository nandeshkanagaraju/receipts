### The three failures, and what to do about each

**A2 cannot clear the gate at city level within realistic bounds.** This is
arithmetic, not judgement:

```
qualifying orders of the A2 model at its two showrooms in August:  76
ALL processed refunds in Dubai that month:                        310
ceiling if EVERY qualifying order were refunded:  +25% of the city's month
```

A 25% move is under two standard deviations of a noisy monthly series. Refunding
more than 100% of the model is not available. **Recommend rephrasing EV-048 from
city level to showroom level**, where the anomaly is real — the same move already
made when EV-048 went from global to city.

**A3 is not measurable as posed.** The delay pushes `settled_on` forward nine
days, which moves those settlements into a *later* week — so the week the question
names loses them rather than showing a longer lag, and the remaining settlements
are unchanged. rel = −0.13%. Either the anomaly must extend the lag on
settlements that stay in the window, or **DV-059 / EV-098 should ask about
unsettled amount at the week's end** rather than average lag within it.

**A4 is closest.** +10.31%, z=1.47, from 3,000 planted orders. One further
increase would likely clear it, and a flagship launch adding 20–25% to a month is
realistic. I stopped rather than tune repeatedly, since each attempt costs a
four-minute regeneration and the decision is yours.

## 2. The generator was not deterministic (item 2)

Before vectorising anything, the same seed gave **637,281 / 636,167 / 637,061**
orders on three runs. That breaks D3, D5, and the claim the project rests on.

The cause is the one D4 warns about: three loops iterated a bare Python `set`.
Python randomises string hashing per process, so each run visited countries in a
different order and drew from the generator in a different order. Pinning
`PYTHONHASHSEED` made it reproducible, which confirmed the diagnosis; sorting the
iterations fixed it properly. Three fresh processes now agree exactly, and
`test_determinism_survives_a_fresh_process` runs three subprocesses because one
process cannot detect this.

This would have stayed invisible until someone tried to reproduce a result, and
would then have invalidated every number computed against the artifact.

### Vectorisation, proved behaviour-preserving

All fifteen per-table Arrow digests are **byte-identical** before and after:

```
15 tables compared, dict-lookup vs vectorised
  SAME  orders  SAME  order_items  SAME  payment_attempts  SAME  refunds
  SAME  settlements  SAME  settlement_items  SAME  fx_rates  SAME  customers
  ... differing tables: NONE
```

The old path is kept as `price_lookup_oracle` and
`test_price_lookup_matches_the_oracle` compares 5,000 rows against it, so the two
agree by evidence rather than by sharing an implementation.

**One correction to the brief:** `data_version` *cannot* be identical across this
change and should not be. SDD §5.4 folds the generator source hash into it
precisely so it moves when the code moves. The per-table digests are the
invariant that matters.

### Scale stays at 0.55

One time-boxed run at 1.0, aborted at **15 minutes**, still inside fact
generation. **Memory was never the constraint** — it peaked near 0.22 GB, an
order of magnitude below my earlier estimate. Time is the cost, and it is
superlinear in a way the profile does not fully explain. `LIMITATIONS.md` records
the shortfall.

untracked, and the freeze records a **SHA-256 per file, hashes only**.


Four tests: hashes match when files are present; the manifest never records
contents (asserted by scanning for `anomaly_id`, `card_network`, `magnitude`,

longer the thing that was sealed.
